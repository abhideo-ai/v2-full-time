01 / Foundations

“Queue” describes several different things.

A queue separates the moment work arrives from the moment work is processed. That separation buys flexibility, but creates questions about waiting, ownership, order, and failure.

Imagine an online store. An order arrives, inventory changes, a fraud check runs, an email is sent, and analytics updates. The email is a job someone should perform. “Order created” is a fact several applications may need to observe. Inside the email worker, a queue may connect a reader thread to a pool of sender threads. These are three different layers.

Start by naming the layer
LayerWhat it meansExample / failure boundary
In-memory data structureEnqueue and dequeue elements inside a process. A concurrent implementation coordinates threads.Java ArrayBlockingQueue. Contents normally disappear when the process dies.
Distributed work queueWorkers compete to receive jobs. Successful work is acknowledged or deleted; failed work can return.SQS or a RabbitMQ work queue. Delivery can repeat after a timeout or failure.
Retained event log / streamAppend records, retain them, and let independent applications maintain reading positions.Kinesis Data Streams or Kafka. Reading does not delete the event; replay lasts only as long as retention permits.

Separate these five decisions

  1. Selection: which item is eligible next—oldest, newest, highest priority, or earliest deadline?
  2. Capacity: what happens when there is no space—wait, reject, drop, or spill to durable storage?
  3. Coordination: how do threads or machines avoid corrupting state or processing conflicting work?
  4. Durability: what survives a process, host, zone, or region failure?
  5. Delivery: when is progress recorded, and can work repeat?

Say it aloud: “Priority tells me which item to choose. Blocking tells me what the caller does when progress is impossible. Durability tells me what survives failure. Those are independent properties, so a queue can be bounded, blocking, priority ordered, and persistent.”

Concurrency means multiple operations are in progress, possibly taking turns on one CPU. Parallelism means operations execute simultaneously, usually on different cores or machines. A thousand waiting network requests are concurrent; they do not require a thousand CPU cores.

Foundations: Java BlockingQueue contract, SQS visibility model, Kinesis concepts.

02 / A taxonomy, not a product list

Queue types and where each fits.

These categories overlap. FIFO, blocking, bounded, and lock-free do not sit on one mutually exclusive menu.

Additional properties to name in an interview

  • Bounded / unbounded: a capacity limit gives a place to apply backpressure. “Unbounded” means no useful application limit; memory and money remain finite.
  • Blocking / nonblocking API: wait for an item/slot, or return immediately. An immediate-return method can still use locks internally.
  • Persistent / ephemeral: disk or replicated storage changes the recovery story and latency.
  • SPSC / MPSC / SPMC / MPMC: single or multiple producers and consumers. An SPSC ring can use a much simpler ownership protocol than a general MPMC queue.
  • Competing consumers / fan-out: workers share one workload, or each independent subscriber gets its own copy/view of every event.

03 / Scheduling

Priority is a scheduling policy.

A priority queue answers “which waiting job should start next?” It does not normally interrupt a job that is already running. If all workers are doing 30-second low-priority jobs, a newly arrived urgent job may still wait.

Use a stable comparison such as (priority, enqueueSequence). In this guide, smaller numbers mean higher priority. The sequence breaks ties in arrival order; without it, equal-ranked jobs need not remain FIFO. Avoid mutating a queued job’s priority without removing/reinserting it or using a supported update operation.

Try the selection rule

The same jobs arrive A, B, C. Compare which waiting job leaves first. Selection order does not imply completion order.

  1. A · priority 3
  2. B · priority 1
  3. C · priority 1

Three jobs are waiting.

How to keep urgent work fast without starving everyone else
StrategyMechanismTradeoff
Strict priorityAlways select from the highest nonempty class.Good urgent latency while capacity exists; low priority can wait forever.
AgingIncrease effective urgency with waiting time.Bounds starvation under suitable load assumptions; needs consistent rank updates or periodic promotion.
Weighted round robinFor example, serve 8 urgent, 3 normal, 1 background job per cycle.Simple share of job counts; unfair in CPU time if job sizes differ significantly.
Deficit round robin / fair queueingBudget by estimated work or bytes, carrying unused credit forward.Better fairness with variable sizes; estimation and scheduler bookkeeping cost more.
Separate pools + reserved capacityReserve some workers for urgent jobs; allow controlled borrowing.Isolation survives a large background backlog, but reserved workers can sit idle.
Deadline schedulingSelect by earliest deadline; expire work that is no longer useful.Needs admission control: sorting impossible deadlines does not create capacity.

Starvation is indefinite waiting because other work keeps winning. Priority inversion is different: an urgent task waits on a resource held by a less urgent task. Short critical sections, resource partitioning, and OS priority inheritance where available address inversion; a priority heap alone does not.

At one million events/s: a single global heap introduces coordination and contention. Partition scheduling, use a few priority classes, and bound outstanding work per tenant. Local heaps sacrifice a perfect global ranking for scalable, approximate priority. Broker prefetch also matters: an urgent item cannot overtake low-priority jobs already delivered to busy workers.

04 / Producer–consumer coordination

What actually blocks in a blocking queue?

If a bounded queue is full, a blocking insertion waits for space. If it is empty, a blocking removal waits for an item. A conventional implementation protects state with a lock and parks waiting threads on conditions such as notEmpty and notFull.

  1. 1. LockCheck capacity under the lock.
  2. 2. Wait if fullRelease the lock while waiting.
  3. 3. RecheckReacquire the lock; check again in a loop.
  4. 4. Insert & signalPublish the item, signal a consumer, unlock.

Why a while loop rather than if? A wakeup does not reserve an item or a slot. Another thread may take it first, and condition waits may wake spuriously. Waiting must atomically release the lock and arrange the wait; inventing “unlock, then sleep” can miss a notification.

Choose the caller’s behavior explicitly
OperationImmediate resultWait indefinitelyWait with deadline
Insertoffer(item) → false if fullput(item)offer(item, timeout, unit)
Removepoll() → null if emptytake()poll(timeout, unit)

A small, bounded handoff

This Java fragment illustrates admission and interruption handling. Job, handle, and RejectedExecutionException setup are omitted; it is not a complete durable worker.

BlockingQueue<Job> queue = new ArrayBlockingQueue<>(10_000);

// Producer: keep waiting time and memory bounded.
boolean admitted = queue.offer(job, 100, TimeUnit.MILLISECONDS);
if (!admitted) {
    throw new RejectedExecutionException("Worker queue is full");
    // The caller must retry, reject, or durably retain the job.
}

// Consumer: this loop runs on a worker thread, not an event-loop thread.
try {
    while (!Thread.currentThread().isInterrupted()) {
        Job next = queue.take();
        handle(next); // Outside the queue's internal lock.
    }
} catch (InterruptedException stopped) {
    Thread.currentThread().interrupt();
}
// Production needs a policy for handle() failure and graceful draining.
Four interview traps
  • PriorityBlockingQueue in Java is logically unbounded. Retrieval can wait, but insertion does not wait for capacity. Add a separate admission bound if you need one.
  • Thread-safe methods do not make a multi-step workflow atomic. if (!q.isEmpty()) q.remove() races; use one removal operation.
  • In Java, actions before insertion happen-before another thread’s access/removal of that element. This publishes prior state; it does not make later mutation of the object safe.
  • A blocked thread generally waits without burning a core. A busy-spin loop burns CPU. An async queue can suspend a task without parking a dedicated OS thread.

Choose an explicit shutdown protocol: stop admission, drain within a deadline, finish or safely requeue active work, then stop workers. Poison-pill sentinels can work, but multiple consumers need the correct number of sentinels and producers must no longer submit behind them. Java’s BlockingQueue interface has no universal close operation.

Contracts: BlockingQueue, PriorityBlockingQueue, Python queue, task tracking, and shutdown.

05 / Scale the work, preserve the invariant

Concurrency is an ownership problem.

First state what must never happen: two charges for one payment, a negative inventory balance, or processing an account’s version 12 before version 11. Then decide which operations may run together. “More threads” is an implementation detail after that decision.

Mechanisms, benefits, and costs

Nonblocking does not necessarily mean lock-free

Lock-free is a progress guarantee: the system as a whole keeps completing operations despite interference, although an individual thread can starve. Wait-free bounds each operation’s algorithmic steps. Neither promises a wall-clock deadline if the OS deschedules the thread. A method that returns immediately on an empty queue may still briefly acquire a lock.

At high throughput, cache-line bouncing and allocations can cost more than the nominal O(1) queue operation. Partition queues, separate frequently written producer/consumer counters to avoid false sharing, batch operations, and measure with realistic payloads. A simple SPSC ring can win when its ownership assumptions actually match the pipeline.

Thread count is not the capacity model

For CPU-bound work, start from CPU time per event and usable cores. For I/O-bound work, start from latency and allowed outstanding operations. On common GIL-enabled CPython builds, threads do not parallelize pure Python bytecode; processes, native code that releases the GIL, or a suitable free-threaded build change that picture. Async I/O is still useful for waiting.

Two concurrency controls that are often confused

A rate limiter—for example, a token bucket—caps admission per unit time and may allow bounded bursts. A concurrency limiter caps outstanding operations. Use both when a destination allows 50,000 requests/s but only 2,000 simultaneous requests. Circuit breakers stop repeatedly calling a failing dependency; they do not create storage for the rejected work.

Say it aloud: “I parallelize across independent keys, keep a serial owner for each ordering key, and bound the number of requests to each dependency. Queue thread safety protects the container; conditional writes and idempotency protect the business effect.”

06 / Correctness under failure

Delivery is not the same as the business effect.

What each promise does—and does not—cover
SemanticsTypical approachFailure consequence
At most onceRecord progress before work; suppress retries.Work may be lost. Suitable only when loss is acceptable.
At least onceRecord progress after successful work; retry uncertainty.Work can repeat. Requires idempotency and adequate retention/retry handling; it is not immunity from expiry or intentional discard.
Exactly-once effect within a boundaryAtomically couple the effect with deduplication/progress, or use an idempotent destination.Depends on the actual transaction boundary. A broker claim does not make an arbitrary email, payment API, or database write execute once.

The unavoidable crash window

1. Read event E.
2. Commit E's business effect.
3. Crash before acknowledging / checkpointing E.
4. Replacement worker receives E again.

If step 2 is not idempotent, the effect may happen twice.
If progress were saved before step 2, a crash could lose the effect.

Give every logical event a stable event_id created before the first send. Preserve it across retries. Kinesis sequence numbers cannot identify producer duplicates: retrying the same logical event can create a second Kinesis record with a different sequence number.

A transactional inbox, with its boundary stated

The following is schematic consumer logic for a database that can atomically write both the inbox and the business tables. The unique key must include the tenant where event IDs are tenant scoped.

BEGIN;
  inserted = INSERT INTO inbox(tenant_id, event_id)
             VALUES (:tenant, :event_id)
             ON CONFLICT DO NOTHING
             RETURNING event_id;

  IF inserted:
      apply_business_change_in_this_same_database();
COMMIT;

// Only now acknowledge, or mark this record complete for checkpointing.

If the effect fails, roll back the inbox insertion too. Do not “mark seen” in one system and perform the effect in another without a recovery protocol. For an external payment API, pass a stable idempotency key and use its documented result/reconciliation contract. For publishing after a DB transaction, write an outbox row in that transaction and relay it later; the relay can publish duplicates, so downstream consumers still need deduplication.

Deduplication has a capacity and retention cost. At 1M events/s, a 24-hour inbox contains 86.4 billion IDs. Even 32 bytes per entry is about 2.76 TB before indexes, storage-engine overhead, and replication. Partition it, size the retention horizon against possible replay, or exploit business-specific unique operations/version checks. An unbounded global “seen IDs” table is not a complete design.

Ordering has four different meanings

  • Production order: the order the business generated events.
  • Append order: the order the service accepted them.
  • Delivery order: the order a consumer received them.
  • Completion order: the order effects committed. Parallel workers can change this even when delivery was ordered.

For a balance update, carry an entity version and require currentVersion == eventVersion - 1 in a conditional update, or use a single serial processor per entity. On a gap, buffer within a bound or reconcile from the source; do not silently accept the newest version if every intermediate event matters.

Work queue acknowledgment vs stream checkpoint

In SQS, visibility is a temporary hiding period, not a lock with an absolute uniqueness guarantee. Delete after successful processing; extend visibility for long work, and expect redelivery after a timeout or crash. In Kinesis, checkpoint a consumer’s reading progress; the underlying record remains until retention expires.

Evidence: AWS producer and consumer duplicates, SQS visibility timeout, Kafka delivery and transaction boundaries.

07 / Queueing math you can use

A queue absorbs a mismatch. It cannot remove it.

Let λ be arrival rate, μ be total sustainable processing rate, and Q be backlog. If λ exceeds μ, backlog grows at approximately λ − μ while that overload lasts. If average arrival rate meets or exceeds sustainable capacity indefinitely, no finite buffer solves the problem.

Backlog growth ≈ max(0, λ − μ) × duration
Time to fill remaining buffer ≈ free slots / (λ − μ), when λ > μ
Drain time ≈ backlog / (μ − λ), when μ > λ

Example: arrivals are 1,000,000/s, processors sustain 900,000/s. The deficit is 100,000/s. A 10-million-event buffer fills in about 100 seconds. With 1,000 bytes/event, the payload alone is 10 GB; object overhead can make an in-memory representation much larger.

Little’s Law: L = λW

For a stable system observed over a suitable interval, average items in the chosen system L equal throughput λ times average time in it W. Define the boundary: waiting queue only, active requests only, or total pipeline. It does not directly predict p99 latency and is not a steady-state solution to a perpetually growing backlog.

  • At 1M events/s and 200 ms average end-to-end residence time, about 200,000 events are in the pipeline on average.
  • At 1M individual I/O operations/s and 20 ms average operation time, about 20,000 operations must be outstanding just to keep up—before headroom.
  • If each event needs 2 ms of actual CPU, the ideal requirement is 2,000 fully busy core equivalents; at a 70% CPU target, about 2,858 cores. Async cannot remove that CPU cost.

Utilization and tail latency

At high utilization, normal variation leaves little room to recover. A toy M/M/1 queue has mean total time 1 / (μ − λ), assuming Poisson arrivals, exponential service times, one server, and a stable system. Real partitioned pipelines rarely meet all those assumptions. Use it to explain the trend, not to promise production p99 latency. Heavy-tailed jobs and hot keys make the tail worse.

Choose an overload policy at every boundary
PolicyBenefitTradeoff / condition
Block / slow producersPropagates pressure upstream.May exhaust request threads or exceed caller deadlines; never block the event loop.
Reject with retry guidanceKeeps memory and latency bounded.The caller must retry or retain work. A rejected event is not an accepted event.
Durable buffer / outboxPreserves admitted work during a temporary outage.Storage, retention, and recovery throughput must all be budgeted.
Drop / sample / coalesceControls overload cheaply.Only for explicitly lossy data; latest temperature may replace older samples, but payment events usually cannot be merged.
Per-tenant quotas / priority poolsProtects critical traffic and prevents a noisy tenant from consuming all resources.Fair allocation can reduce global utilization; distinguish guaranteed share from spare capacity.

Use retry budgets, exponential backoff with jitter, and a finite retry horizon. If every failed request is retried immediately, effective arrival rate rises exactly when capacity is lowest. Pause polling when a local processing queue is full; ensure client prefetch is bounded too. One bounded queue surrounded by unbounded buffers is still an unbounded system.

08 / Amazon Kinesis Data Streams

Stream, shard, partition key: three different concepts.

Kinesis Data Streams is a managed, retained event stream. Producers append records; consumer applications read them independently and track progress. AWS manages the underlying service infrastructure.

Stream
A named collection of shards, with settings for capacity, retention, encryption, and access. Think “orders-events,” not one single FIFO list.
Shard
An ordered sequence of service records and a unit of read/write capacity. Each active shard owns a range of the 128-bit hash-key space. Many partition keys can share one shard.
Partition key
A producer-supplied string—such as order_id. Kinesis normally hashes it with MD5 and maps the resulting number to the shard whose hash range contains it. It is a routing/ordering choice, not a separately provisioned resource.
Partition
A generic division of data. In Kafka, a topic partition is a first-class log. In Kinesis, the closest capacity/log equivalent is a shard. A Kinesis partition key is not a Kafka partition and is not one shard per key.
Record
A data blob plus partition key, with a service-assigned sequence number after acceptance. A KPL aggregate can contain multiple logical application events inside one Kinesis record.
Sequence number
A position identifier used with shard context. Do not compare it as a global offset across shards or treat it as an event timestamp. Aggregated user records also need a subsequence position.
Retention
The period records remain readable after insertion: 24 hours by default, configurable up to 365 days. Consuming or checkpointing does not delete them.
Consumer application
A logical reader such as fraud detection or analytics. Each application can independently read the same stream. Within one application, workers divide the work.
Shard iterator / subscription
A polling cursor used with GetRecords, or an enhanced fan-out subscription using SubscribeToShard. A transient iterator is not your durable checkpoint.

The shard capacity model

For sustained planning, a shard supports up to 1,000 Kinesis records/s and 1 MB/s of writes; both constraints must be satisfied. Shared polling has a 2 MB/s read budget per shard, shared across readers, and five GetRecords calls/s per shard. Enhanced fan-out gives each registered consumer its own read throughput of up to 2 MB/s per shard.

Record size is not sustained throughput

The default maximum record size is 1 MiB. Current Kinesis supports configuring records up to 10 MiB for occasional large payloads. This uses burst capacity; it does not turn a shard into a sustained 10 MiB/s write lane. PutRecords currently accepts up to 500 records and 10 MiB per request including partition keys. Check every downstream integration before enabling larger records.

For large documents or images, often put the object in S3 and send a small reference with an immutable object version, checksum, and access policy. Coordinate object retention with event replay; an event pointing to a deleted object is no longer reproducible.

Verified sources: Kinesis terminology, current quotas, large-record behavior, PutRecords contract, enhanced fan-out.

09 / Ingestion

Partition for correctness, then check the distribution.

If order matters per order, order_id is a natural candidate. If it matters per customer, customer_id may be necessary—but a very active customer can become a bottleneck. “Use a random UUID” distributes work but discards entity affinity; “use tenant ID” may concentrate a large tenant on one shard.

Key choice defines a scaling boundary
KeyBenefitRisk
Entity IDCo-locates the entity’s events.One hot entity cannot automatically spread over multiple shards.
Random event IDUsually high cardinality and good distribution.No per-entity ordered lane; ordering must be unnecessary or reconstructed elsewhere.
Tenant + entityPreserves entity affinity and tenant context.Still check frequency distribution; cardinality alone does not prove balance.
Salted entity + bucketSplits one entity’s traffic into parallel subkeys.Loses total order for that entity. Merge/reorder or use commutative partial aggregates only where semantics permit.
ExplicitHashKeyLets advanced producers choose a hash position.Creates routing/resharding responsibilities; can undermine same-key affinity if used inconsistently.

A hot key is not the same as a hot shard

A shard can be hot because many distinct keys collide within its range; splitting the range can help. If a single key alone generates more than one shard’s sustained byte budget, both split children still do not share that one hash value. You must reduce volume, aggregate when record-count limited, change the key semantics, or accept that the ordering requirement is the bottleneck. Adding unrelated shards does not fix it.

Batching vs aggregation vs compression

  • Batching / KPL collection: put many Kinesis records in one HTTP request. It reduces request overhead but does not reduce the records counted against a shard’s 1,000 records/s limit.
  • KPL aggregation: pack several logical events into one service record. This reduces the service record rate and can help small events escape the record-count limit. Consumers must deaggregate and checkpoint correctly.
  • Compression: reduce bytes on the stream. It costs producer and consumer CPU and may reduce inspectability. Kinesis does not transparently compress/decompress arbitrary application payloads for you.

Set flush bounds on count, bytes, and time. A producer that waits to fill a giant batch during low traffic can violate the latency objective. Bound outstanding batches, use persistent connections, and inspect each item’s result. A successful HTTP response from PutRecords can contain failed records.

Retries can reorder records

Producer submits A, then B with the same partition key.
PutRecords: A fails; B succeeds.
Producer retries only A; A now succeeds.
The retained stream may contain B, then A.

PutRecords does not guarantee ordering. Retry known failures with backoff and jitter; avoid blindly resending acknowledged successes. If the entire response is lost, the result is uncertain and retry can duplicate accepted records.

For strict sequencing, serialize writes for the relevant key using PutRecord, wait for the preceding result, and use SequenceNumberForOrdering with the preceding returned sequence number. Its documented guarantee is for the same client and partition key. Multiple independent producers need a business-level sequencer/ownership rule, and ambiguous responses still require duplicate handling. Alternatively, carry event versions and explicitly reorder with bounded buffers and a gap policy.

The cost of strict sequencing: if each acknowledged write takes 10 ms in an illustrative deployment, one serial producer lane can issue only about 100 writes/s. Distribute across many independent keys. Strict global order for all one million events/s requires global coordination; challenge whether the business actually needs it.

Details: PutRecord ordering parameter, partial failures and ordering, KPL collection and aggregation, aggregated record identity.

10 / Reading and processing

Three separate dimensions of consumer parallelism.

  1. Across applications: fraud, analytics, and archival each read the events they need. More independent readers multiply read traffic.
  2. Across shards within an application: workers divide shard ownership. More shards create more independently owned processing units.
  3. Inside one owned shard: the application can process independent keys concurrently, but must preserve ordering and checkpoint correctness itself.
Read transport is independent of application worker count
MechanismBudget and behaviorTradeoff
Shared pollingGetRecords: up to 2 MB/s total per shard across readers, five calls/s. A call can return up to 10,000 records / 10 MB; a large response constrains subsequent calls.Simple; readers compete for capacity. Polling intervals add latency and recovery reads need spare bandwidth.
Enhanced fan-out (EFO)SubscribeToShard pushes records over a subscription with up to 2 MB/s dedicated per registered consumer per shard.Separates readers’ throughput budgets and usually reduces delivery latency; quotas and pricing depend on mode.

Kinesis Client Library: workers, leases, and checkpoints

KCL coordinates workers using DynamoDB metadata. Within a KCL application, a shard lease is assigned to one worker, and a worker can own multiple shards. KCL creates a record processor per owned shard, handles shard discovery, and reassigns leases when workers stop or fail. Separate logical applications use separate application identities/metadata.

With 100 open shards and 20 workers, roughly five shards per worker is a simple illustration, not a guaranteed balancing outcome. With 200 workers, you do not get 200 simultaneous exclusive owners of those 100 open shards in the same application. Extra workers may be idle; parent-shard draining and lease transitions can complicate the instantaneous picture.

Current KCL 3.x balances using worker utilization information. Its metadata layout is version dependent: three tables by default, with a consolidation option from KCL 3.5. Size and permission the metadata store too; it is part of the working system.

The checkpoint must follow durable completion

Checkpointing every event adds write overhead; checkpointing every N records or T seconds reduces overhead but increases possible replay. Approximate replay exposure per shard is its processing rate × checkpoint interval, plus outstanding work. Always handle lease loss: stop starting work and do not assume the old worker can safely commit later.

Use serial lanes by partition key, a bounded execution pool, and a completion tracker. Checkpoint the highest contiguous completed prefix only. Completed events beyond a slow gap may be replayed after failure, so their effects must be idempotent. Bound this gap: one stuck event must not cause unbounded buffered completion state.

Lambda consumers

A Lambda event source mapping reads batches and invokes the function. ParallelizationFactor ranges from 1 to 10 concurrent batches per shard; AWS maintains partition-key ordering within that model. Actual concurrency is also limited by available records, keys, account/function quotas, and downstream capacity. More parallelization does not increase Kinesis read bandwidth.

Batch size and batching window trade invocation overhead against latency. The invocation batch payload limit is 6 MB, so a larger stream-record allowance is not a promise that Lambda can accept that record. Use partial batch failure reporting and/or batch bisection where appropriate, cap retry age/attempts deliberately, and configure an on-failure destination. Kinesis itself has no automatic per-record DLQ.

Aggregation with Lambda needs explicit compatibility checks

AWS documents partition-key restrictions when combining aggregation and parallelization. Without EFO, contained events need matching partition keys for ordered processing; with EFO, some incompatible aggregated events can be dropped without reaching a failure destination. Prefer a supported producer/consumer combination and test the exact aggregation format and routing before deployment.

Stateful stream processing

For windows, joins, event-time processing, and managed keyed state, consider a stream processor such as Apache Flink. Event time is when an event happened; processing time is when your worker handles it. Watermarks express progress assumptions about event time, allowing windows to close while defining what to do with late arrivals. Framework checkpoints can recover state, but exactly-once external effects still depend on sink support.

Split and merge: what happens to the records?

  • Split: replace an open shard’s hash range with two child ranges. New records route to the children.
  • Merge: combine adjacent hash ranges into a child shard when reducing provisioned capacity.
  • Old records: parent shards retain their existing records until retention expiry. They do not move wholesale into the new shard.
  • Consumers: finish the relevant parent shard(s) before processing the child to preserve key order across the transition. KCL tracks this lineage.
  • Operations: scaling and discovery take time and APIs have limits. Resharding is not a synchronous emergency response to an already full buffer.

On-demand manages shard scaling; explicit split/merge and UpdateShardCount workflows are for provisioned mode. More shards can increase aggregate throughput and distribute multiple hot keys, but still cannot spread one unchanged hot key across independent ordered lanes.

Verify before an interview or deployment: capacity modes and warm throughput, regional quotas, resharding, parent/child processing metadata.

12 / The architecture interview

Design for one million events per second—continuously.

The target is a rate, not a complete requirement. Translate it into bytes, keys, work, fan-out, retention, and recovery before choosing a shard count.

Step 1 · Establish the workload contract

Ask for average/p95/max event size; sustained duration; peak-to-average ratio; end-to-end latency; allowed loss and duplication; ordering scope; number of independent readers; per-event CPU/I/O; sink throughput; retention/replay; Region; and outage recovery target. Distinguish generated, durably accepted, and successfully processed events/s.

Worked example assumptions—not measured performance

1,000,000 logical events/s; 1,000 effective bytes/event including amortized stream record/key overhead; no aggregation; broadly balanced keys; three full-stream consumer applications; an illustrative 70% maximum planned shard utilization; a 60-second consumer outage; and a desired five-minute catch-up after recovery. MB, GB, and TB in the arithmetic are decimal. One MiB is 1,048,576 bytes. Using 1,000,000 bytes/s for the documented 1 MB/s shard budget is a conservative planning convention.

Step 2 · Size record rate and byte rate independently

R = logical events/s ÷ logical events per Kinesis record
D = logical events/s × effective bytes per logical event
Nwrite = ceil(max(R / 1,000, D / 1,000,000) / utilization)

Without aggregation: R = 1M records/s and D = 1 GB/s. Both produce a 1,000-shard theoretical minimum. At 70% planned utilization, ceil(1000 / 0.70) = 1,429 shards. “30% headroom” here means 30% of installed capacity remains unused at the plan rate; it does not mean simply multiplying by 1.3.

Step 3 · Budget producers and the network

With 500 records per full PutRecords request, 1M service records/s requires at least 2,000 requests/s across the producer fleet. Small batches, size limits, uneven flushing, and retries increase that. If average request latency is 50 ms, roughly 100 concurrent requests are needed just to sustain that ideal rate; choose a bound with measured headroom.

1 GB/s is 8 Gbit/s of raw payload. Base64 encoding in the JSON API increases the data representation by about one third before protocol/TLS overhead; other transport details matter too. Distribute producers, reuse connections, and measure serialization CPU, network paths, endpoint limits, and retry amplification. Capacity budgets and billing units are not the same as wire bytes.

Step 4 · Budget every reader

Three applications reading all records consume about 3 GB/s of logical stream reads in steady state. At 1,429 shards, shared read capacity is approximately 2.858 GB/s, so shared polling cannot support all three full-rate readers even before recovery.

/ (2,000,000 × utilization))

Choose EFO for reader isolation, or size enough shared-read shards and enforce polling budgets. EFO gives each application its own per-shard budget, making 1,429 write-sized shards sufficient for this example’s steady-state read bytes. It does not prove the processors or sinks can keep up.

Step 5 · Size actual processing, including the destination

If one worker instance demonstrably processes 5,000 events/s at the chosen latency and resource target, 200 active instances per full-stream application are the arithmetic minimum. Add failure and recovery capacity. If 5,000/s is its saturation maximum rather than its safe operating point, divide again by your utilization target.

Do not write “one DB insert per event” without a capacity model. A 500-event sink batch at 1M events/s is 2,000 batch operations/s, but the database still processes one million records/s unless the semantics allow reduction or aggregation. Shard the data model, use bulk writes, bound connections, verify index/write amplification, and load-test conditional/idempotent writes.

Step 6 · Plan recovery while the stream keeps arriving

A 60-second consumer outage accumulates 60 million events, about 60 GB at 1,000 bytes/event. After recovery, a consumer processing 1.3M/s while 1M/s continues arriving drains that backlog in 200 seconds. Processing at exactly 1M/s never catches up.

μrequired = λ + backlog / desired drain seconds
μrequired = 1,000,000 + 60,000,000 / 300 = 1,200,000 events/s

For three readers all catching up at 1.2M/s, shared read sizing at 70% becomes ceil(3.6 GB/s / 1.4 MB/s) = 2,572 shards. EFO isolates each reader’s 1.2 GB/s; 1,429 shards provide enough per-reader byte headroom under the example assumptions. CPU, the sink, and key skew can still prevent five-minute recovery.

A producer outage is a different case: events that never reached Kinesis are not protected by Kinesis retention. Durably buffer them upstream. Uploading the backlog while live traffic continues requires extra write capacity; size that separately.

Step 7 · Understand the daily economics

1M events/s means 86.4 billion/day. At 1,000 bytes each, one day holds 86.4 TB of logical data; seven days hold about 604.8 TB before compression and service implementation overhead. Three full readers consume about 259.2 TB/day of logical reads before replay. These are volume estimates, not the number of physical disks or an AWS invoice.

Compare provisioned shard-hours, PUT payload units, EFO consumer-shard/read charges where applicable, on-demand ingest/retrieval rounding and commitments, extended retention, DynamoDB metadata, worker compute, sink costs, logs, and data transfer. Use the Region’s current calculator. Aggregation can materially change per-record billing; cost per logical event is more useful than API-call count alone.

Two-minute design answer: “At one million events per second, I first establish bytes, ordering scope, and processing cost. With 1,000 effective bytes per event and no aggregation, the aggregate write floor is 1,000 shards; an illustrative 70% utilization target gives 1,429. I validate key skew and account quotas, and pre-provision or warm capacity. Three full readers exceed the shared read budget at that shard count, so I evaluate enhanced fan-out. Each application has bounded key-ordered processing, idempotent sinks, and checkpoints after durable completion. I size recovery above live traffic: one minute of backlog needs 1.2 million events per second to drain in five minutes. I prove the whole path under sustained load and failure, including the destination.”

How to know the system is keeping up.

Common failure scenarios and recovery rules

  • Poison event: retry transient errors; quarantine deterministic bad data after a bounded policy. Persist event ID, source position, schema version, error, and enough payload/reference for repair. If skipping breaks entity order, stop/reconcile that entity explicitly.
  • Consumer dies after sink commit: replay is expected; the sink’s idempotency boundary must absorb it.
  • Lease changes while old work runs: cancel/drain appropriately. Use destination fencing or version conditions if stale writes could violate the invariant.
  • Database outage: slow or pause consumption, retain source data, and alarm before lag approaches retention. Recovery capacity must exceed live arrival rate.
  • Backlog approaches retention: oldest unread records may expire. Increase retention early where allowed, restore processing, and plan archive replay; extending retention cannot restore already expired records.
  • Region outage: Kinesis’s in-Region durability is not automatic cross-Region continuity. Define RPO/RTO, routing failover, destination state, and duplication/order reconciliation for any independent replication design.

A sustained-load acceptance plan

  1. Specify pass/fail targets first: 1M durably accepted logical events/s for the required duration; a concrete p99 effect latency; allowed error/loss; maximum lag; and recovery deadline. The duration must represent the real demand—e.g., a 24-hour run for an all-day workload.
  2. Use realistic distributions: sizes, serialization, tenant/key skew, slow events, bursts, duplicates, and downstream I/O. Test fresh-stream/ramp behavior separately from warmed steady state.
  3. Measure every stage: generated, accepted, read, completed, duplicated, quarantined, and expired events; CPU, allocations/GC, network, connection pools, and sink saturation.
  4. Inject failures: kill workers, pause the sink, force partial write failures/timeouts, lose leases, and reshard while traffic continues. Confirm no checkpoint passes unfinished work.
  5. Prove catch-up under live load: the 60-second outage test should demonstrate the chosen five-minute recovery objective, rather than stopping producers to make the graph improve.
  6. Reconcile identity: compare produced event IDs and expected business effects using partitioned audit data. Counts alone can hide one missing event and one duplicate.
  7. Run beyond the short burst: check sustained rate limits, scaling lag, retention, memory growth, and cost. A fast in-memory microbenchmark does not establish end-to-end throughput.

Use least-privilege producer/consumer roles, encryption in transit and at rest, appropriate KMS permissions, schema compatibility rules, and tenant-aware authorization at ingestion. Keep sensitive event bodies out of routine logs; sampled traces and aggregate metrics are usually more practical at this rate.

Four distinctions worth remembering

NATS Core versus JetStream

Core NATS delivers to connected subscribers with at-most-once behavior; it does not provide replay of missed messages. JetStream adds persistence, acknowledgment state, and redelivery. Its retention policy matters: a work-queue policy retires acknowledged jobs differently from a stream retained for independent readers.

Redis Lists versus Streams

A destructive pop removes a list item before processing; a worker crash can lose that job unless you build a processing-list/recovery protocol. A Streams consumer group records pending deliveries. XACK marks an entry handled for that group; it does not by itself delete the stream entry. Reclaim abandoned pending work and coordinate trimming with recovery.

Pulsar Shared versus Key_Shared

Shared spreads messages among consumers without ordered delivery. Key_Shared routes a key’s work to the same consumer under its dispatch model, enabling parallelism across keys. Compatible batching is required; negative acknowledgments/redelivery can still affect order. Configure retention if acknowledged messages must remain available for replay.

Can SQS handle a million messages per second?

SQS Standard is designed for very high throughput, but the full pipeline still needs an in-flight and API budget. At 1M messages/s and 1 second from receive to delete, about one million messages are in flight on average. The commonly documented Standard in-flight limit is approximately 120,000 messages per queue, so validate/increase applicable quotas or partition the workload and reduce residence time.

Batch APIs support up to 10 messages. Even with full batches, 1M messages/s needs at least about 100,000 send, 100,000 receive, and 100,000 delete requests/s across the fleet. Real receives may return smaller batches. FIFO high-throughput quotas are regional and per API action; current top listed default is 70,000 TPS, or 700,000 messages/s with full batches in selected Regions. Do not assume creating more queues bypasses an account/Region quota.

Can Kinesis act as a priority queue?

A shard is append ordered. You cannot move a later urgent record ahead of an earlier record in the retained log. You can read ahead and prioritize local processing, but then completion order changes and checkpoints can be held back by old work. For urgent jobs, prefer separate priority queues/streams and reserved consumer capacity, or route relevant events from a stream into a work-queue layer. Every extra hop adds latency, cost, and another delivery boundary.

16 / Rehearsal

Answer, then defend the boundary.

Cover the answer, speak for 30–60 seconds, then expand it. A strong answer states the requirement, mechanism, tradeoff, failure behavior, and how you would measure it.

1. What is the difference between a queue and a stream?

A work queue distributes jobs among workers and retires acknowledged jobs. A retained stream stores a sequence of events and gives independent applications their own positions and replay. Both may internally partition work and redeliver after failure.

Follow-up: Does every worker receive every event? Only separate fan-out applications do; workers within one competing group normally divide the work.

2. Is a priority queue always a blocking queue?

No. Priority specifies selection order; blocking specifies waiting behavior. Java has both PriorityQueue and PriorityBlockingQueue. The latter blocks retrieval when empty but is logically unbounded, so insertion does not wait for capacity.

3. How would you implement a bounded blocking queue?

Use a fixed buffer, head/tail/count, one lock, and not-empty/not-full conditions. Wait in a loop, releasing the lock while parked; after waking, reacquire and recheck. Change state under the lock, signal the opposite side, and execute the business job outside the queue lock. Include cancellation and shutdown.

4. Why might a lock-free queue be slower?

CAS retries, cache-line contention, memory allocation, and reclamation can outweigh lock overhead. Lock-free is a progress property, not a throughput guarantee. Compare proven implementations under the actual producer/consumer counts, payloads, batch sizes, and latency targets.

5. Does FIFO guarantee the results finish in order?

No. FIFO selection/delivery can feed parallel workers; a short second job may finish before a slow first job. If effects must be ordered, serialize within the required key or use version checks and an explicit reorder/commit protocol.

6. How do you prevent low-priority starvation?

Use aging, weighted or deficit scheduling, and reserved capacity. Strict priority can starve lower classes under sustained urgent traffic. A fair scheduler also needs admission control: if total demand exceeds capacity, no scheduler meets every deadline.

7. What is a Kinesis shard versus a partition key?

A shard is an ordered log segment and capacity unit with a hash range. A partition key is the string a producer supplies to choose a hash position. Many keys map to a shard; the same key maps to one active shard at a time under normal routing. Resharding changes the range ownership.

8. How many shards for one million messages per second?

First ask whether “messages” means logical events or Kinesis records and ask for effective bytes/event. Without aggregation, the record-rate floor is 1,000 shards. At 1,000 effective bytes/event, the byte-rate floor is also 1,000; at 70% planned utilization, 1,429. Then check read fan-out, recovery, key skew, and quotas.

9. Will batching solve the 1,000-records/s shard limit?

PutRecords batching reduces HTTP requests, not service record count. Aggregating multiple logical events into a Kinesis record reduces that count. Once bytes dominate, aggregation alone does not create bandwidth; compression or more capacity may be necessary.

10. A shard is hot. Should you split it?

If several keys collectively overload a hash range, splitting may distribute them. If one key itself exceeds the sustained shard budget, it still maps to one child. Salt or decompose the key only if the ordering semantics permit it; otherwise the per-key requirement is the bottleneck.

11. Is Kinesis ordered?

There is shard-local append order, not a global order across shards. PutRecords and retries can change intended producer order. For strict per-key sequencing, coordinate the producer, use the appropriate serial PutRecord contract or business versions, and preserve order through processing and sink commit.

12. Why did adding consumer instances not improve throughput?

Check whether shard leases already have owners, whether read bandwidth is exhausted, whether one key is hot, or whether the sink is saturated. More workers do not make one shard’s service bandwidth larger. Add the kind of parallelism that addresses the measured limit.

13. When would you choose enhanced fan-out?

When independent applications need isolated per-shard read throughput or lower delivery latency. At 1 GB/s ingest and 1,429 shards, three full readers need 3 GB/s, exceeding shared capacity of about 2.858 GB/s. EFO separates those budgets, subject to mode-specific pricing and registration limits.

14. When is it safe to checkpoint concurrent work?

After durable success of every earlier delivered record in that shard. If 101, 103, and 104 are complete but 102 is unfinished, the checkpoint stays at 101. Record completion in delivery order and advance the contiguous prefix. Replayed later completions must be idempotent.

15. Is end-to-end exactly once possible?

Within a well-defined boundary, yes: atomically couple the business effect with deduplication/progress or use a destination’s idempotency protocol. Broker delivery claims alone do not cover external effects. Name the transaction boundary and explain the crash after the effect but before acknowledgment.

16. Can on-demand instantly handle a sudden 1M/s launch?

Do not assume that. Standard on-demand has starting capacity, growth behavior, and Region limits. For a known launch, provision capacity or configure supported warm throughput and verify readiness. A single hot partition key remains constrained.

17. How much spare capacity is enough?

Derive it from variance, the slowest key, failure tolerance, and recovery time. For 1M/s arrivals and 60 seconds of backlog, catching up in five minutes requires 1.2M/s processing after recovery. Check readers and the sink too. A blanket “add 20%” without a recovery model is weak.

18. How do you handle a poison record without losing order?

Classify the error and use bounded retries. Persist a quarantine record before considering the event handled under an explicit skip policy. If later events depend on it, pause that key and repair/reconcile it. Skipping and preserving strict dependent event order are conflicting requirements unless the business defines a resolution.

19. What would you measure in a million-per-second benchmark?

Durably accepted and completed logical events/s, bytes, p99 effect latency, lag, throttling, duplicates, missing effects, key skew, CPU/GC, network, sink behavior, and cost. Sustain the load for the required duration and inject failures while live traffic continues. Reconcile event identities, not only counts.

20. What is the strongest reason to reject a proposed design?

It fails a stated invariant or has no capacity/recovery evidence at a critical boundary. Examples: global ordering is promised over independently processed shards; checkpoints pass unfinished work; or an upstream million-per-second claim feeds a sink proven at only 100,000/s. Explain the concrete failure and a feasible alternative.

  1. 0–5 minutes: clarify semantics, bytes, latency, duration, and recovery requirements.
  2. 5–12: estimate write/read/CPU/storage rates; identify ordering and hot-key limits.

17 / Quick reference

Terms you should be able to explain simply.

Backpressure
A signal or constraint that slows admission when downstream work cannot keep up.
Head-of-line blocking
One slow or unavailable item prevents later items in the same ordered lane from progressing.
Idempotency
Repeating the same logical operation has the same intended effect as performing it once.
Deduplication
Recognizing that an operation/event has already been seen; useful only with an appropriate retention and atomicity policy.
Lease
Temporary ownership that can move to another worker after expiry or failure.
Fencing
Rejecting stale owners’ writes, usually using a monotonically increasing ownership token or a comparable version condition enforced by the destination.
Checkpoint / offset
A durable progress position for recovery. The exact representation differs by system.
Replay
Reading retained events again. It may require a separate application identity, an earlier start position, and replay-safe sinks.
Consumer lag
How far a reader or completed processor is behind the source; specify whether measured in time, records, or bytes.
Fan-out
Delivering the same event set to multiple independent applications.
Prefetch / credits
How much work a client can receive ahead of completion; affects memory, fairness, and unacknowledged work.
Partition affinity
Routing related work to the same owner/lane so state or order stays local.
Commutative operation
An operation whose order relative to another does not change the result under the stated model. This can permit parallel partial aggregation, but duplicates still need handling.
RPO / RTO
Recovery point objective: acceptable data loss window. Recovery time objective: acceptable time to restore service. Restoring service and fully draining backlog may be separate objectives.
p99
The latency at or below which 99% of observed operations fall. Measure at the user-relevant boundary and over a meaningful workload.
